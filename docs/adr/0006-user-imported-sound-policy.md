# ADR 0006: ユーザー取り込み音源の制限を利用権限ポリシーとして扱う

- 状態: Accepted
- 日付: 2026-07-15
- 関連: `docs/assets-spec.md`, `docs/domain-model.md`, `docs/architecture.md`

---

## Context（背景・制約）

現在の音源選択は、アプリに同梱した `AlarmSoundCatalog` の音源を選ぶ方式である。
将来、ユーザーが端末ストレージ上の任意音源を取り込み、Timer / Alarm / Preset から
選択できるようにする。

取り込み音源には次の制約が必要になる。

- 端末・codec 差を考慮した対応形式の限定
- 過大なファイルによるコピー時間、保存容量、再生準備コストの抑制
- 登録件数と全音源の合計容量の制限
- 将来、利用権限に応じて上限を拡張できる構造
- 課金機構を Domain の音源モデルや Timer / Alarm / Preset に混入させないこと

現時点の配信形態は「無料・広告なし・アプリ内課金なし」である。ここで定義する
買い切り枠は、将来課金を採用した場合に既存の音源モデルを変更せず上限だけを拡張する
ための予約仕様である。課金方式は買い切りとし、現行アプリで課金機能を提供している
ことを意味しない。

---

## Decision（決定事項）

### 1. 音源制限を利用権限ポリシーとして注入する

容量、時間、登録件数、対応形式を固定のプラン名から直接参照せず、現在の利用権限から
解決した制限ポリシーとして Application 層へ渡す。

ポリシーが保持する値は次のとおり。

- 1 ファイル容量上限
- 時間上限
- 登録可能件数
- 対応形式

全音源の合計容量上限は独立した設定値にせず、常に次式から導出する。

`1 ファイル容量上限 × 登録可能件数`

これにより、表示上限と登録判定の不一致を防ぐ。

### 2. 初期利用枠と将来拡張枠

| 利用枠 | 1 ファイル容量上限 | 時間上限 | 登録可能件数 | 合計容量上限 |
| --- | ---: | ---: | ---: | ---: |
| 通常枠 | 5 MB | 3 分 | 3 件 | 15 MB |
| 将来買い切り枠 A | 10 MB | 6 分 | 5 件 | 50 MB |
| 将来買い切り枠 B | 15 MB | 9 分 | 10 件 | 150 MB |

内部処理は少なくとも 1 ファイル 25 MB / 15 分まで扱える構造とする。これは公開上限ではなく、
将来上限を拡張しても型、コピー処理、メタデータ取得、再生準備を作り直さないための
設計余裕である。

将来拡張枠は買い切りによる恒久的な利用権限とする。買い切り商品と枠 A / B の対応、
価格、購入復元の実装詳細は課金機能の着手時に決定する。

### 3. Domain と課金機構を分離する

- Domain は Pure Dart を維持し、課金 SDK、商品 ID、プラン名を参照しない。
- Timer / Alarm / Preset は引き続き `String soundId` のみを保持する。
- Domain に Android URI、外部絶対パス、`File` を持ち込まない。
- 課金を実装する場合も、課金状態を利用権限へ変換する処理は Infrastructure / Application
  側に閉じ込め、音源登録処理には解決済みポリシーだけを渡す。

### 4. ファイルをアプリ内部ストレージへ取り込む

外部 URI を再生時まで参照し続けず、選択時に検証したファイルをアプリ内部ストレージへ
コピーする。元ファイルの移動・削除や SD カード取り外しに鳴動の信頼性を左右されないためである。

DB には安定した `soundId`、表示名、形式、実ファイルサイズ、再生時間、内部保存先を
解決する情報を保存する。取り込み音源を解決できない場合は同梱デフォルト音へ
フォールバックする。

### 5. 形式・容量・空き容量を安全側で検証する

- 初期対応: MP3、Ogg Vorbis / Opus、PCM WAV、AAC / M4A
- 拡張子だけでなく MIME type、ヘッダー、実デコード可否を検証する。
- 形式または再生時間を確定できないファイル、破損ファイルは登録しない。
- 容量は `1 MB = 1,000,000 bytes` で統一する。
- 取り込み前または取り込み後の端末空き容量が 10 GB 未満になる場合は登録しない。
- 容量取得に失敗した場合も登録しない。

### 6. 管理操作とライフサイクルを決定する

- 最短再生時間は 1 秒とし、PCM WAV は初期段階で 8 / 16-bit に限定する。
- 音源選択 sheet から追加し、独立した管理画面で試聴、改名、削除を行う。
- 初期表示名は拡張子を除く元ファイル名とする。
- プレビューは本番と同じアラーム音量経路を使用する。
- 内容ハッシュで同一ファイルの重複登録を防ぐ。
- 使用中音源の削除時は、全参照を同梱デフォルト音へ一括置換する。
- 音源置換時の上限判定では旧音源を除外し、新音源の確定までは旧音源を保持する。
- 取り込みは一時ファイルを使い、DB とファイルの両方が確定した場合だけ成功とする。
- 通知からのコールド起動でも Repository を初期化し、`soundId` から内部コピーを解決する。
  解決処理は期限付きとし、固定 3200 ms のハンドオフ境界を延長しない。
- 空き容量はアプリ内部保存先と同じストレージボリュームを基準に判定する。
- 初期実装では OS バックアップと端末移行の対象外とし、アンインストール時に削除する。
- 取り込み音源は外部送信しない。

---

## Consequences（結果・トレードオフ）

### 利点

- 将来課金を追加しても、音源 Entity や Timer / Alarm / Preset の DB 参照方式を変更せず、
  制限ポリシーの差し替えだけで対応できる。
- 合計容量を導出値にするため、件数や 1 ファイル上限との矛盾が生じない。
- アプリ内部コピーにより、アラーム発火時の外部ストレージ状態への依存を排除できる。
- 形式、容量、空き容量を登録前に検証するため、失敗を鳴動時まで持ち越しにくい。

### 欠点・トレードオフ

- 元ファイルとアプリ内部コピーで端末容量を二重に使用する。
- 対応形式ごとのメタデータ取得・デコード検証と実機テストが必要になる。
- 空き容量の割合取得はプラットフォーム依存となり、Infrastructure 実装と失敗時の
  エラー表示が必要になる。
- 将来買い切り課金を実装する場合は、商品構成、価格、購入復元、オフライン時の権限確認を
  別途決定する必要がある。

### 制約として受け入れる点

- ユーザー音源のトリミング、変換、音量正規化は初期実装に含めない。
- 買い切り利用権限は恒久的に有効とする。
- ユーザー取り込み音源は端末内利用に限定し、アプリから外部送信しない。

---

## Alternatives Considered（検討した代替案）

### A. 外部 URI をそのまま保存して再生する

- 利点: 内部ストレージを追加消費しない。
- 欠点: 元ファイルの移動・削除、権限失効、SD カード取り外し、端末ロック状態に左右される。
- 却下理由: アラーム用途では再生時の信頼性を優先する。

### B. 通常枠の上限をコードへ直接ハードコードする

- 利点: 初期実装が単純。
- 欠点: 将来の利用権限追加時に UI、検証、テストへ条件分岐が散在する。
- 却下理由: すでに複数の将来枠を想定しており、制限ポリシーとして集約する方が変更範囲を
  抑えられる。

### C. 取り込み時にアプリ内で共通形式へ変換・正規化する

- 利点: 再生形式と音量を統一できる。
- 欠点: Native codec または変換ライブラリ、処理時間、電力、ライセンス、失敗時処理が増える。
- 却下理由: 初期実装として過大。対応形式を限定し、実デコード検証を行う。
